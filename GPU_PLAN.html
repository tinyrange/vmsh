Architecture and delivery plan

First-party 3D acceleration for vmsh

Start on a Darwin/ARM64 host, add standard VirGL acceleration to cc, render it through a first-party Go implementation, and present shared GPU textures through native Glass and a vendored Gowin platform layer. The host-sharing experiment starts in SquadVM. The product goals are accelerated neuroimaging applications in Neurodesk and Steam/Proton gaming in SquadVM or a dedicated gaming frontend.

Standard Mesa guest First-party host renderer Gowin submodule 2D fallback preserved Darwin/ARM64 first

01 · Decision

Own the host graphics stack

vmsh will implement and ship its own VirGL command processor and OpenGL renderer. The guest continues to use the standard Linux virtio-gpu DRM driver and Mesa VirGL driver; the first-party boundary begins at the host side of the virtio device.

Committed direction: virglrenderer and rutabaga are not runtime dependencies. They may be used in development as behavioral oracles, command-stream references, and differential test targets.
  • Guest ABI Standard virtio-gpu plus the existing VirGL capset and command stream.
  • Host renderer A new Go implementation owned by vmsh, initially scoped to an honest, deliberately small capset.
  • Presentation Shared OpenGL resources produced on a renderer thread and sampled by native Glass on its window thread.
  • First host Darwin/ARM64 with HVF, an ARM64 Linux guest, NSOpenGL shared contexts, and native Glass.
  • Product ladder Accelerate Neurodesk first; preserve a backend-neutral route toward Vulkan, Metal, and translated x86 Steam games.
  • Fallback The existing CPU framebuffer and display.Session.Snapshot path remains a supported mode.
02 · Scope

Goals and non-goals

Goal

Useful Neurodesk acceleration

Neurodesk's Xorg desktop, compositing, visualization tools, and ordinary OpenGL applications render through the Apple GPU rather than llvmpipe.

Goal

Darwin-first, portable core

Prove the stack over Hypervisor.framework first while keeping the virtio device and VirGL renderer portable to KVM and WHP.

Goal

Native Glass integration

The renderer and visible Gowin window share GPU resources with explicit synchronization and no window-thread violations.

Goal

Truthful compatibility

Guest capabilities are generated from implemented behavior intersected with host support. Unsupported features are never advertised optimistically.

North star

Steam-class gaming

Preserve a path for translated x86-64 Steam and Proton workloads, guest Vulkan, a Metal-capable host renderer, game input, audio, and low-latency presentation.

Out of scope for the first release Reason Revisit condition
Venus and guest Vulkan Required for the Steam north star, but it needs blob resources, host-visible memory, context initialization, and a Metal-capable Vulkan renderer. Neurodesk VirGL is stable on Darwin/ARM64 and the backend-neutral renderer contract is proven.
GPU or PCI passthrough Breaks portability and introduces platform-specific privilege and device ownership. Only as an independent expert feature.
Video encode/decode commands Large additional API and security surface unrelated to desktop 3D. A concrete product workload requires it.
3D VM snapshots Host GL object state is not currently serializable and display snapshots are already restricted. A renderer-neutral state format exists.
Full OpenGL feature parity The first release must advertise only the subset proven by conformance tests. Expanded incrementally from real workloads.
03 · Baseline

What exists today

cc already has the correct device position and most lifecycle connections. The missing layer is the host interpretation of 3D resources and command buffers.

Guest

DRM-ready image

The guest kernel enables CONFIG_DRM_VIRTIO_GPU. Neurodesk and SquadVM publish ARM64 images. SquadVM uses Xorg's modesetting driver; the same standard Mesa VirGL path can accelerate both images once a host capset is exposed.

cc

Portable 2D virtio GPU

One MMIO device already serves KVM, HVF, and WHP. It implements scanout, 2D resources, backing attachment, transfers, flush, cursor, input, resize, and interrupts.

Glass

CPU scanout upload

Native frontends poll framebuffer snapshots and upload dirty XRGB8888 regions with gl.TexSubImage2D before drawing a fullscreen textured quad.

Cross-architecture baseline: the ARM64 SquadVM image already installs qemu-x86_64, registers it through binfmt_misc, and carries essential AMD64 runtime libraries. That proves the packaging shape, but Steam-class performance requires a JIT-oriented translator with graphics API forwarding rather than treating qemu-user as the final CPU path. 
guest resource
    │ TRANSFER_TO_HOST_2D + RESOURCE_FLUSH
    ▼
cc/internal/virtio.Framebuffer (CPU XRGB8888)
    │ Snapshot(rect, generation, incremental)
    ▼
display.Session
    │ dirty byte slice
    ▼
native Glass → gl.TexSubImage2D → visible Gowin window

Relevant code: cc/internal/virtio/gpu.go, cc/internal/virtio/display.go, cc/display/display.go, and cmd/squadvm/display.go.

04 · Architecture

Target data path

Keep the standard guest driver and the portable cc device. Insert a first-party renderer behind a narrow interface, then give Glass an optional native-frame path alongside its existing CPU snapshots.

Guest applications OpenGL, Xorg glamor, compositor
→
Mesa VirGL Gallium state and TGSI command stream
→
virtio-gpu DRM resources, contexts, submissions, fences
cc virtio-gpu transport, guest memory, resource ledger, used rings, IRQs
→
vmsh VirGL renderer validation, Gallium state, TGSI lowering, host GL calls
→
Gowin share group offscreen renderer context, sync, visible window context

The two rows are connected by the virtqueue. The renderer never invokes GL on a vCPU or window event thread.

Boundary rule: cc understands virtio-gpu and resource accounting, but treats submitted VirGL words as an opaque renderer payload. vmsh understands VirGL. Gowin understands native windowing and host graphics contexts, but not VM protocols.
05 · Ownership

Repository and package boundaries

Owning the stack does not require collapsing the layers. Each repository should own the protocol closest to its existing purpose.

cc/
Guest-facing virtio-gpu device, standard commands and responses, guest-memory transfers, resource/context IDs, descriptor lifetime, fences, IRQ delivery, and CPU framebuffer fallback.
vmsh/
First-party VirGL decoder and renderer, TGSI compiler, acceleration policy, native Glass integration, diagnostics, compatibility corpus, and end-to-end behavior tests.
gowin/
Platform graphics bindings, starting with OpenGL share groups, offscreen contexts, current-context execution, synchronization, and visible window presentation. A later Metal surface/device API follows the same ownership boundary.
guest image
Standard Linux virtio-gpu kernel driver, Mesa VirGL driver, Xorg modesetting configuration, and diagnostic applications.

06 · Dependency ownership

Vendor Gowin as a sibling submodule

Gowin should follow the same source ownership model as cc: a reviewed commit pinned in the vmsh tree and selected by a local Go module replacement.

Bootstrap policy: add gowin/ first at the commit represented by the currently consumed module version (8be60804d51a). This makes vendoring behavior-neutral. Update to a newer Gowin commit in a separate reviewed change. 
git submodule add -b main https://github.com/tinyrange/gowin.git gowin
git -C gowin checkout <full commit for 8be60804d51a>

# go.mod
replace github.com/tinyrange/gowin => ./gowin

Required repository changes

  1. Add a gowin entry to .gitmodules with branch = main, matching the cc convention.
  2. Add the local replace directive while retaining a meaningful required module version for tooling and provenance.
  3. Update README repository layout and requirements to name both required submodules.
  4. Add gowin/go.sum to dependency cache keys where it materially improves CI caching.
  5. Confirm all checkout jobs use submodules: recursive. Release and test workflows already do; publishing and Pages jobs should be evaluated based on whether they compile native frontends.
  6. Make tools/build.go fail early with a useful diagnostic when either submodule is absent.

Update discipline

Update

Advance intentionally

Update the Gowin pointer in its own commit, record notable API or platform changes, and run native build and window smoke tests before mixing renderer work into the same change.

Rollback

Move one pointer

A broken platform update is recoverable by returning the submodule pointer to the last tested commit. Do not copy patched module-cache files into vmsh.

07 · Host execution

GL context and thread model

Context ownership is a correctness contract, not an optimization. Gowin must make the legal calling thread explicit and must support a renderer context that shares objects with the visible window. 

UI goroutine                         Renderer goroutine
runtime.LockOSThread()               runtime.LockOSThread()
        │                                    │
visible Gowin context                offscreen shared context
        │                                    │
poll events / compose UI             decode / validate / issue GL
        │                                    │
wait on render fence  ◀────────────── glFlush + published NativeFrame
        │

Gowin interfaces

type ShareGroup interface {
    NewOffscreenContext(ContextOptions) (Context, error)
    NewWindow(WindowOptions) (Window, error)
    Close() error
}

type Context interface {
    Run(func(gl.OpenGL) error) error
    Capabilities() Capabilities
    Close() error
}

type Window interface {
    Context() Context
    Poll() (Event, error)
    Swap() error
    Close() error
}
  • Every Context.Run executes on its permanently locked OS thread.
  • The renderer receives no raw native window handle and cannot pump UI events.
  • The UI receives an opaque native-frame token rather than mutable renderer state.
  • Window destruction does not destroy the share group until the renderer has stopped.
  • Context loss transitions the display to a structured failed or 2D-fallback state.
Forbidden: executing host GL from GPU.Write, a vCPU exit, a virtqueue notification goroutine, or an arbitrary display polling goroutine.

09 · First-party renderer

VirGL command processor

A submitted buffer is a sequence of 32-bit words. Each command has an 8-bit command, 8-bit object type, and 16-bit payload length. The parser must completely validate framing before dispatch.

  1. Frame Read the command header, reject zero progress, overflow, truncation, excess size, and unknown mandatory encodings.
  2. Decode Convert words into typed, immutable command values using checked field widths and enumerations.
  3. Validate Resolve context-local handles, resource types, formats, levels, ranges, and required state without calling GL.
  4. Plan Translate the command into renderer operations and update a shadow copy of Gallium state.
  5. Execute Issue host GL operations on the renderer context thread and record an explicit fence when requested.

Initial command surface

Class First implementation Deferred until required
Objects Blend, rasterizer, depth/stencil/alpha, shader, vertex elements, sampler view/state, surface Queries, streamout, MSAA surface
Framebuffer Viewport, framebuffer attachments, scissor, clear, blend color, stencil reference Conditional render and advanced multisample state
Input Vertex buffers, index buffer, constant buffers Indirect multi-draw and atomic buffers
Textures Sampler states/views, inline write, copy region, basic blit Shader images and uncommon compressed formats
Execution Clear and direct DRAW_VBO Compute launch, tessellation, geometry, streamout
Contexts Main context; add sub-contexts when the captured Mesa baseline proves they are required Cross-context sharing beyond the guest ABI contract
This table is a hypothesis, not the capset. Before freezing the first supported subset, capture command streams from the exact Mesa baseline used by SquadVM. If Mesa requires a command during initialization, it belongs in the earliest viable slice even if the test scene appears not to use it.

Capability rule

advertised capability
    = implemented and behavior-tested
    ∩ available in the current host GL context
    ∩ allowed by the selected compatibility profile

Host extension discovery alone never enables a guest feature. A feature bit becomes visible only after the corresponding command, state interaction, shader lowering, and negative validation paths are implemented.

10 · Compiler

TGSI to host GLSL

Shader translation is the deepest independent subsystem. Treat it as a checked compiler pipeline rather than string substitution. 

TGSI text from guest
    ↓ bounded lexer
tokens + source locations
    ↓ parser
typed TGSI syntax tree
    ↓ verifier
register files, declarations, control flow, sampler types, limits
    ↓ lowering
small renderer IR + stage interface
    ↓ GLSL emitter
#version 330 core source
    ↓ host compiler + link
cached GL program or structured diagnostic
Compiler contract

Never trust declarations

Validate register indexes, masks, source counts, immediates, nesting depth, control-flow targets, stage legality, and sampler compatibility before emitting GLSL.

Host contract

One conservative baseline

Request OpenGL 3.3 core or better on all platforms. Begin with GLSL 330 and explicitly lower guest behavior that differs from the host profile.

Program cache

Key the full interaction

Cache by shader content plus renderer state that changes emitted interfaces or patching. Never assume a shader handle uniquely identifies a host program.

Diagnostics

Preserve both sides

Debug traces should correlate TGSI, generated GLSL, host compile logs, context ID, and submission sequence without logging guest data by default.

First compiler scope

  • Vertex and fragment stages only.
  • Declarations, immediates, inputs, outputs, constants, temporaries, and system values used by the baseline.
  • Arithmetic, comparison, conversion, texture sampling, derivatives, and structured control flow required by desktop shaders.
  • Interpolation and linkage validation between stages.
  • Coordinate, depth, point-size, clip, and front-face conventions covered by rendered-pixel tests.

Geometry, tessellation, and compute stages remain disabled in the capset until their compiler and state paths are complete.

11 · Data model

Resources, formats, and guest memory

cc ledger

Guest-visible identity

Resource ID, creation parameters, backing entries, attached contexts, scanout references, outstanding transfers, and destruction state.

Renderer object

Host-visible identity

GL target/name, storage allocation, format mapping, dimensions, mip levels, layers, synchronization state, and memory charge.

Phase-one memory policy

  1. cc validates every guest backing entry using checked address + length arithmetic.
  2. Transfers copy guest bytes into renderer-owned native or Go byte storage during the call; the renderer does not retain a pointer into movable Go memory.
  3. The renderer uploads or reads data on its GL thread using bounded staging buffers.
  4. Transfer-from-host copies completed bytes back through cc's GuestMemory interface.

Later, stable mapped guest ranges may eliminate copies, but only after KVM, HVF, and WHP expose a common pinned-region contract with explicit lifetime and teardown.

Format table requirements

  • Single authoritative mapping for VirGL format, GL internal format, upload format, type, component class, block dimensions, and bytes per block.
  • Creation rejects formats absent from both the implementation profile and host capabilities.
  • Transfer validation uses block geometry rather than assuming four bytes per pixel.
  • Depth/stencil, integer, normalized, sRGB, and renderability properties are distinct flags.
  • Scanout begins with XRGB8888/BGRA-compatible color resources; other formats require an explicit conversion path.
No retained guest pointers: a C-free implementation still has pointer-lifetime risks if a renderer goroutine keeps a slice that aliases hypervisor mappings during VM teardown. Ownership and cancellation must be explicit.
12 · Concurrency

Virtqueues, submissions, and fences

Current queue processing is synchronous under the GPU mutex. 3D completion must become asynchronous without losing virtio ordering or allowing a guest reset to race late renderer callbacks.

  1. Consume descriptor Copy the request and command buffer into bounded device-owned memory.
  2. Validate envelope Check virtio header, context, resource references, output descriptor capacity, and fence metadata.
  3. Submit work Enqueue an immutable renderer job and release the GPU lock immediately.
  4. Execute and fence The renderer thread processes commands in context order and creates a host GL synchronization point.
  5. Retire Completion reacquires device state, verifies the generation, writes the response, advances the used ring, and raises the IRQ.

Required invariants

  • Each accepted descriptor is retired exactly once.
  • A fenced descriptor is not visible in the used ring before renderer completion.
  • Fence fields are echoed according to the negotiated virtio contract.
  • Completions from a pre-reset renderer generation are discarded safely.
  • Destroy waits for or cancels queued jobs before releasing resource state.
  • No GL call occurs while holding the device mutex.
  • Queue backpressure is bounded and produces a deterministic device error rather than memory growth.

Start with one serialized renderer queue per VM. Parallel contexts are an optimization only after ordering and teardown behavior are proven.

13 · Presentation

Scanout and native Glass

Deliver acceleration in two presentation stages. The first validates rendering without changing the public display session. The second removes the readback and upload.

Stage A

CPU-compatible scanout

On flush, read the rendered resource into the existing XRGB8888 framebuffer. Glass continues polling snapshots and uploading dirty rectangles. This is slower but preserves VNC, screenshots, and the entire current display contract.

Stage B

Shared native frame

Publish an opaque frame containing a shared texture reference, size, generation, damage, and synchronization token. Glass waits, samples it in its context, swaps, then releases the frame. 

type NativeFrameSession interface {
    AcquireFrame(context.Context, uint64) (NativeFrame, error)
}

type NativeFrame interface {
    Size() (width, height uint32)
    Generation() uint64
    Damage() image.Rectangle
    Present(Presenter) error
    Release()
}

The optional interface must not expose a raw GL texture name through ccvmd's JSON API. Texture identity is meaningful only inside a share group and process. CPU snapshots remain authoritative for VNC, headless clients, and fallback.

Synchronization protocol

  1. Renderer finishes all writes to the scanout texture.
  2. Renderer inserts a GL fence and flushes the producer context.
  3. Renderer atomically publishes the frame generation and fence.
  4. Glass waits on the fence in the consumer context before sampling.
  5. Glass releases its reference after the swap no longer needs the frame.
  6. Renderer reuses or destroys the texture only after all frame references are released.
Resize: preserve the current long-lived session model. A resize is a state transition that creates a replacement scanout, signals the guest, and retires the old shared frame after both renderer and Glass references drain.

15 · Product ladder

Two workloads, one extensible device boundary

Neurodesk and Steam exercise different graphics generations. VirGL is the shortest route to useful scientific visualization and a reliable desktop; it is foundation work for gaming, not the entire gaming stack.

Neurodesk ARM64 native Linux tools, Xorg, OpenGL visualization
→
First-party VirGL Gallium state and TGSI to host OpenGL
→
NSOpenGL + Glass shared texture presentation on Darwin/ARM64
Steam / Proton x86-64 CPU translation plus DXVK or vkd3d-proton
→
Guest Vulkan path virtio resources and first-party command virtualization
→
Metal + Glass backend-neutral native frames and low-latency input
Track A · First

Neurodesk on Apple Silicon

ARM64 Linux guest over HVF, standard Mesa VirGL, first-party TGSI renderer, NSOpenGL 4.1 host context, and shared-texture native Glass presentation.

Track B · North star

Steam and Proton

A performant x86/x86-64 translator, forwarded graphics and system libraries, Vulkan-capable virtio resources, a Metal host backend, controller/audio integration, and frame pacing.

VirGL alone is not a modern Proton solution. DXVK translates Direct3D 8–11 to Vulkan and vkd3d-proton implements Direct3D 12 over Vulkan. The first release should therefore optimize for Neurodesk without claiming Steam compatibility from OpenGL acceleration alone.

Architecture decisions to make reusable now

  • The cc renderer interface negotiates context/capset types rather than assuming every future context is VirGL.
  • Guest blob and host-visible resource support can be added without replacing 2D or VirGL resource accounting.
  • NativeFrame remains opaque: it may carry a shared GL texture today and a Metal texture or IOSurface later.
  • Glass input, audio, frame pacing, and presentation lifecycles remain independent from renderer command decoding.
  • CPU translation is a guest execution service, not code embedded in the GPU renderer.

Portability rules

  • Platform files create and bind contexts; the renderer contains no GLX, Objective-C, or WGL calls.
  • The common GL interface exposes required operations and typed constants uniformly.
  • Missing host operations reduce the advertised capset or reject acceleration; they never become silent no-ops.
  • Renderer correctness is tested against both core-profile semantics and known host-driver differences.
  • The Darwin implementation is the reference lifecycle implementation; Linux and Windows adapt the same contracts rather than redefining them.
17 · Trust boundary

Security and resource governance

The guest controls the VirGL byte stream. Treat the renderer as an untrusted-input parser with access to a sensitive host driver API.

Validate

Before GL

Lengths, multiplication, offsets, handles, formats, levels, layers, masks, enum values, shader complexity, and object state are checked without invoking the host driver.

Budget

Per VM

Charge resources, staging buffers, shader source, compiled programs, contexts, queued words, outstanding fences, and trace storage to explicit limits.

Contain

Fail one context

Invalid commands fail the offending guest context or device operation. They do not panic the daemon, leak host state, or poison unrelated VM sessions.

Initial limits

Exact defaults should be chosen from desktop traces, but every dimension must exist before acceleration is enabled:

  • maximum command words per submission and queued across the VM;
  • maximum resources, contexts, sub-contexts, shaders, and object handles;
  • maximum texture dimension, layer count, mip levels, and samples;
  • maximum total estimated GPU bytes plus CPU staging bytes;
  • maximum TGSI source bytes, tokens, declarations, instructions, registers, and control-flow depth;
  • maximum in-flight fences and maximum retained completed frames;
  • bounded diagnostic capture disabled by default.

Hardening path

  1. Pure Go parser and renderer in-process with strict budgets and fuzzing.
  2. Renderer health watchdog and context-loss containment.
  3. Optional per-VM renderer worker process if host driver isolation becomes necessary.
  4. Platform sandboxing for the worker without changing the cc renderer contract.
Go memory safety is not the whole boundary. Valid but adversarial shaders and GL state still reach native host drivers. Parser safety, resource limits, and eventual process isolation are separate requirements.
18 · Operability

Diagnostics, tracing, and recovery

State

Structured renderer status

Renderer profile, host GL vendor/renderer/version, negotiated capset, resource usage, last completed fence, queue depth, context-loss state, and fallback reason.

Trace

Capture and replay

A versioned, bounded trace records decoded commands, resource metadata, and selected payloads. The replay tool runs without a VM to reproduce rendering and parser failures.

Diagnostic levels

Level Default Contents
Operational On Renderer selection, capset identity, initialization/fallback, context loss, fatal device errors.
Metrics On, aggregated Submissions, words, upload/readback bytes, draw count, shader compiles, cache hits, fence latency.
Command trace Off Typed command stream with bounded resource payload capture.
Shader trace Off TGSI, checked IR, generated GLSL, and compile/link log.

Logs should identify VM, context, submission, and fence using stable structured fields. User-facing prose is not a test contract.

19 · Verification

Behavior-level testing strategy

Tests protect guest-visible behavior, isolation, and rendered results. Avoid tests that merely freeze helper structure, exact internal GL call sequences, fallback ordering, or UI wording.

Layer User bug it catches Test form
virtio protocol Guest hangs, wrong responses, early fences, lost interrupts Descriptor-chain tests with exact structured responses, used-ring state, and IRQ behavior.
Decoder Malformed guest stream crashes or corrupts the daemon Table tests for protocol boundaries plus persistent fuzz targets for every command family.
TGSI compiler Valid applications fail compilation or produce wrong pixels Checked IR tests, host compile tests, and rendered shader cases.
Renderer state Textures, depth, blending, scissor, or indexing render incorrectly Small scenes with sampled-pixel assertions and tolerances where the API permits variation.
Glass handoff Tearing, stale frames, resize corruption, context-thread crashes Frame generation, fence, release, resize, detach, and close behavior under repeated rendering.
Guest integration Mesa falls back to software or the desktop fails to start Boot a VM, verify structured DRM/capset state, render a known scene, and inspect resulting pixels.
Fallback Unsupported hosts lose graphical display entirely Force renderer initialization failure and prove auto still provides a functioning 2D desktop.
Lifecycle Repeated VM use leaks or poisons the daemon Start, render, resize, stop, and restart VM-backed contexts repeatedly in one daemon session.

Compatibility corpus

  • The live ARM64 SquadVM corpus is images/gpu-glmark2: it runs glmark2's complete 33-scene built-in suite, including build, texture, shading, bump, effects, desktop, buffer updates, complex models, conditionals, functions, and loops.
  • The representative application workload is images/gpu-openarena: stock OpenArena 0.8.8 runs as an ordinary GLX/OpenGL 2.0 application against Mesa VirGL. Its deterministic 1,200-message bot-match slice covers renderer and map initialization, GLSL compilation, model and texture loading, animated gameplay, and repeated dynamic-buffer updates.
  • The browser workload is images/gpu-firefox: Firefox ESR runs four local WebGL scenes covering indexed depth-tested geometry, render-to-texture with a post-processing pass, dynamic additive point sprites, and a procedural fragment shader. Structured telemetry and guest gl.readPixels captures prove that every scene rendered through VirGL rather than merely reaching the host window.
  • The fixture builds on astra-pi5, boots under systemd, selects the host-preferred DRM mode, requires an XRGB/depth visual, identifies the guest renderer as virgl, and loops without an environment-variable gate.
  • Next add resize and reattach cycles, WebGL 2 coverage, and a second representative native application trace with a materially different renderer profile.
  • Add Neurodesk visualization traces when the renderer moves from the host-sharing experiment into the neuroimaging product slice.
  • Replay traces against the first-party renderer in CI using software host GL where necessary.
  • Optionally replay the same traces through virglrenderer during development and compare output; do not require it for normal builds.
  • Add a new trace only when it represents an important user workflow or a real fixed bug.
End-to-end workflow: exercise acceleration within a long-lived vmsh/Glass session—select or create the VM-backed system, render repeatedly, resize or reattach, run ordinary commands, then return to @host. A one-shot boot is not sufficient to validate session lifecycle.
20 · Delivery

Implementation milestones

Milestones are gated by observable behavior rather than dates. Each slice leaves the existing 2D path working.

M0

Own Gowin source Implemented

Gowin is now a pinned sibling submodule, selected locally through go.mod, covered by recursive checkout and dependency caching, and checked by the repository build helper before a build starts.

Current evidence: vmsh, cc, ccvm, ndappx, and squadvm build and sign on Darwin/ARM64; the release matrix remains the clean-clone cross-platform gate.
M1

Shared NSOpenGL contexts Implemented

Gowin now creates a shared NSOpenGLContext on a dedicated locked renderer thread and exposes serialized execution plus explicit fence, wait, flush, and deletion operations. Its Darwin integration test exercises the producer/presenter ownership contract independently of guest graphics.

Current evidence: the Gowin Darwin test performs 16 alternating fenced updates with exact FBO pixel readback before clean teardown. Guest OpenGL is not credited to this milestone; it must pass through the M2–M4 virtio-gpu and VirGL path. Resize soak remains ongoing hardening.
Cube acceptance boundary: a host-side demo or a guest script sending scene parameters is not an accelerated guest application. Acceptance requires a regular Mesa OpenGL process in the ARM64 guest, a negotiated virtio-gpu 3D device, VirGL command submission and fence completion, host GPU execution, and the guest scanout presented by Glass. The reproducible test guest lives in images/gpu-cube, and all development runtime state stays beneath the repository through explicit -cache-dir and -storage options.
M2

Asynchronous cc 3D transport Live, synchronous fences

Renderer injection, VirGL feature negotiation, capset queries, contexts, 3D resources, scatter/gather transfers, opaque submissions, fenced responses, and renderer scanout are implemented and exercised through a fake renderer. Submission is deliberately synchronous in this first slice; queued execution and asynchronous fence retirement remain the hardening step.

Current evidence: protocol tests cover capsets, context/resource lifecycle, backing transfer, opaque submit, fence identity, and renderer-to-framebuffer scanout without a host GL dependency.
M3

Bounded VirGL decoder Firefox WebGL profile live

Bounded framing, contexts, resource and object handle tables, vertex/rasterizer/framebuffer/shader state, sampler views and states, depth targets, indexing, multi-buffer vertices, texture transfers, blits, validation, and explicit unsupported-command errors are implemented. The TGSI compiler now links unnamed varyings and translates the sampler, arithmetic, integer, indirect-addressing, discard, and structured-control-flow instructions exercised by the complete SquadVM glmark2 corpus and OpenArena. Fragmented shader submissions are reassembled with strict size and offset checks. Host resources remain alive while referenced by surfaces, sampler views, or draw bindings, and dynamic buffer uploads preserve their authoritative guest data. Rasterizer point-size and sprite-coordinate state maps Gallium generic inputs onto native point coordinates, and texture/buffer readback now returns real host-rendered bytes across split virtio guest backing.

Current evidence: malformed framing and unsupported TGSI are rejected; standard kmscube renders continuously; all 33 stock OpenGL ES glmark2 benchmarks complete; stock OpenArena loads 114 GLSL shaders, a full map, models, textures, HUD, and animated bot combat; and Firefox sustains four distinct WebGL workloads through Mesa VirGL without a rejected renderer operation.
M4

First accelerated guest cube Implemented

The initial TGSI vertex/fragment compiler translates Mesa's real declarations, immediates, swizzles, write masks, arithmetic, dot, reciprocal-square-root, and varying semantics to GLSL. Guest buffers, constants, surfaces, framebuffer state, viewport, clears, rasterizer culling, and triangle-strip draws execute on a dedicated accelerated Darwin OpenGL context. The result is read back through the existing CPU framebuffer for Glass and VNC.

Current evidence: Debian ARM64 kmscube reports Mesa renderer “virgl”, remains active across continuous KMS page flips, sustains roughly 440 frames/second in the native run, and produces distinct, correctly culled 1440×900 framebuffer captures over time.
M5

SquadVM application profile Firefox WebGL implemented

The reproducible ARM64 images/gpu-glmark2 guest expands the cube into a regular application corpus covering the complete built-in glmark2-es2-drm suite: VBO and client-vertex upload paths, indexed draws, all core primitive modes used by the suite, texture and mipmap sampling, varyings, 24-bit depth, depth-only shadow passes, render-target blits, integer shader operations, indirect constants, and repeated scene cycles. Separate fixture launches also verify clean context teardown and recreation. It runs as an ordinary systemd service and keeps all host cache, storage, and capture artifacts beneath the repository. The companion images/gpu-openarena fixture then runs a stock desktop game through Xorg, GLX, OpenGL 2.0, and the same owned VirGL decoder. Its build derives a deterministic benchmark from OpenArena's installed data rather than vendoring game assets. The images/gpu-firefox fixture adds a regular browser and WebGL 1 application, runs entirely from a loopback origin, refuses a non-VirGL Xorg renderer, and records structured browser telemetry plus one guest-rendered PNG for every scene.

Current evidence: the glmark2 guest reports Mesa/X.org, renderer “virgl”, OpenGL ES 2.0, and completes all 33 stock scenes. The OpenArena guest reports direct rendering, renderer “virgl”, OpenGL 2.0 and GLSL 1.20; its 1440×900 timedemo completes 1,201 rendered frames in 54.5 seconds (22.0 fps on the M4 Darwin/ARM64 development host, improved from the initial 15.1 fps baseline). Firefox ESR reports Mesa/X.org and WebGL 1.0, visits all four 1440×900 scenes at 60 fps in the final Darwin run, and produces distinct non-black guest readbacks for indexed cubes, framebuffer post-processing, dynamic point sprites, and a procedural shader.
M6

Native shared-texture scanout Implemented on Darwin

Gowin exposes the visible window's complete NSOpenGL share group. cc publishes leased frames from a bounded three-texture pool with producer and consumer fences, generation, damage, release, and resize-safe teardown. Glass samples those textures directly. CPU readback is deferred until a VNC or diagnostic snapshot explicitly requests it.

Current evidence: a renderer behavior test proves that a native flush performs zero readbacks and that the first CPU snapshot performs exactly one lazy readback; Gowin's cross-context fence test verifies shared texture ownership; and the native 1440×900 guest corpus runs through the shared-texture path at roughly 2,000–4,400 frames/second in early scenes versus roughly 500–1,000 through VNC readback. Repeated resize and attach soak remains ongoing hardening.
M7

Linux, Windows, and SquadVM portability

Implement GLX and WGL share groups, fill common GL binding gaps, intersect capsets with each host, add SquadVM traces, and run the same renderer corpus on all supported native desktop targets.

Exit gate: the standard guest scene and desktop behavior pass on KVM, HVF, and WHP with 2D fallback verified independently.
M8

Hardening and default-auto rollout

Tune budgets, complete long-running stress and fuzz campaigns, validate context-loss recovery, establish performance telemetry, and change NeurodeskAppX from opt-in VirGL to auto on qualified Darwin/ARM64 hosts.

Exit gate: acceleration can be enabled by default without weakening VM lifecycle reliability or unsupported-host behavior.
21 · Performance

Performance gates

Correctness gates delivery. Performance measurements decide when to remove temporary copies and when acceleration should become the default.

Measure Stage A expectation Stage B expectation
Guest rendering Clearly faster than llvmpipe for a representative 3D scene despite scanout readback. Host GPU remains the dominant renderer with no scanout readback bottleneck.
Frame handoff Measured GPU readback and texture-upload bytes are visible in diagnostics. Normal frames share a texture and perform only synchronization plus composition.
Input latency Renderer work cannot block the window event loop or VM input device path. Fence waits are bounded and do not serialize unrelated UI composition.
Daemon stability Long-running render, resize, stop, and restart cycles show no unbounded resource or goroutine growth.

Avoid brittle timing assertions in ordinary unit tests. Maintain a repeatable benchmark harness and compare distributions or profiles during development and release qualification.

22 · Risk register

Primary risks and responses

Risk Impact Response
VirGL compatibility surface is larger than the first trace suggests. Desktop initializes but ordinary applications fail. Honest capset, pinned Mesa baseline, trace corpus, feature-by-feature expansion, differential testing.
TGSI translation dominates implementation effort. Long path from triangle to usable desktop. Separate compiler architecture, narrow stages/features, compiler-focused tests and diagnostics.
Host GL differences create platform-only failures. Works on the Darwin reference host but not Linux or Windows, or depends on behavior outside macOS's frozen OpenGL 4.1 profile. Conservative GL 3.3 core contract, capability intersection, common rendering corpus, real-host lanes.
The VirGL implementation becomes an OpenGL-shaped product boundary. A later Vulkan/Metal renderer requires invasive display and resource rewrites. Keep capset negotiation, cc resources, native frames, and presentation handles backend-neutral from the first change.
qemu-user is mistaken for the final Steam CPU architecture. The Steam client may start experimentally while games remain unusably slow or incompatible. Measure CPU translation separately and require a JIT plus native graphics-library forwarding before gaming claims.
Asynchronous completion races VM teardown. Use-after-free, double retirement, daemon crash. Renderer generations, explicit cancellation, single owner queue, lifecycle stress tests.
Shared texture lifetime is coupled to the window. Detach or resize destroys resources still in use. Share-group ownership above the window, reference-counted native frames, ordered shutdown.
Guest input reaches a fragile host driver. Denial of service or host compromise. Complete pre-GL validation, budgets, fuzzing, watchdogs, and a future worker-process boundary.
Multiple accelerated VMs compete for a process-global renderer. Resource collisions or incorrect isolation. The first-party renderer is instance-scoped from the start; global caches are immutable or keyed by renderer identity.
Submodule development becomes confusing. Detached-head work or unreviewed dependency drift. Document update flow, pin reviewed commits, keep Gowin pointer changes isolated, verify recursive clones.
23 · North-star track

Path from VirGL to Steam on Apple Silicon

Steam gaming on a Darwin/ARM64 host is a combined CPU, graphics, media, and product problem. It should build on the same VM and Glass lifecycle, but it needs a second graphics protocol beyond VirGL.

Two independent translations are required: most of the Steam catalog and Proton runtime is x86/x86-64, while modern Windows games reach Vulkan through DXVK or vkd3d-proton. CPU translation and GPU virtualization must therefore be designed and measured separately.
CPU execution
Replace the current qemu-user compatibility baseline with a gaming-capable JIT and syscall/runtime strategy. Evaluate a FEX-class design with x86 and x86-64 support, per-application tuning, and native library forwarding.
Guest runtime
Steam, Wine/Proton, an x86-64 root filesystem, 32-bit runtime support where required, DXVK, vkd3d-proton, persistent game storage, and reproducible per-title configuration.
GPU protocol
Blob resources, host-visible mappings, context initialization, Vulkan command serialization, synchronization, memory budgets, and a first-party host implementation.
Apple GPU
A Metal-capable backend. MoltenVK is a useful compatibility reference and development oracle, but is not assumed to be a shipped dependency under the first-party ownership decision.
Product shell
Low-latency controller, keyboard, mouse, audio, frame pacing, fullscreen/window transitions, overlays, persistent libraries, and clean VM stop/restart behavior.

GPU protocol decision gate

Candidate Advantage Darwin constraint Plan position
Venus-compatible guest ABI Standard Mesa guest driver and an existing Vulkan serialization model. Current Venus host assumptions center on native Vulkan and external/host-visible memory behavior that cannot be copied blindly onto Metal. Preferred guest-facing starting point; feasibility spike required.
First-party Vulkan-to-Metal backend Full control over resource lifetime, presentation, and Apple GPU integration. Very large Vulkan semantics, shader, synchronization, and compatibility surface. North-star ownership direction; scope only after measured prototype work.
Vendored Vulkan portability implementation Fastest way to test whether the remaining VM and CPU stack can run games. Does not satisfy a strict first-party renderer goal and may expose portability-subset gaps needed by DXVK/vkd3d-proton. Allowed as a development oracle or temporary experiment, not an assumed product dependency.
VirGL/OpenGL only Already delivered for Neurodesk and older native OpenGL software. Does not provide the Vulkan feature model expected by current Proton translation layers. Fallback and legacy path, not the gaming architecture.

Gaming-track gates

  1. G0 · Native ARM64 Vulkan experiment Render a Vulkan scene from an ARM64 Linux guest through candidate virtio resource and Metal-host paths, before adding x86 translation.
  2. G1 · Vulkan memory and synchronization contract Prove blob resources, host-visible mappings, queues, semaphores, fences, presentation, reset, and teardown over HVF.
  3. G2 · Translated x86-64 Vulkan Run a translated x86-64 Vulkan diagnostic and scene with native graphics API forwarding and measured CPU overhead.
  4. G3 · Steam and Proton runtime Start Steam reliably, maintain a persistent library, launch Proton, and preserve controller/audio/input behavior across sessions.
  5. G4 · Curated game vertical slice Run one explicitly selected DXVK title from installation through gameplay with correct pixels, input, audio, save data, and clean shutdown.
  6. G5 · Compatibility and latency program Expand title coverage, frame pacing, shader/pipeline caching, fullscreen behavior, controller support, and per-title diagnostics without claiming universal Steam compatibility.
Frontend decision can wait: begin inside SquadVM to reuse its ARM64 image, x86 packaging, persistent home, Glass, and release machinery. Split out a gaming-specific frontend only when its library, controller, fullscreen, update, and lifecycle requirements materially diverge from SquadVM.
24 · Completion

Definition of done for the VirGL foundation

The first program is complete when acceleration is a reliable property of a long-lived Neurodesk session on Darwin/ARM64, not merely when one demo draws. Steam then advances through the separate gaming-track gates without reopening these foundations.

  • Gowin and cc are pinned sibling submodules and a clean recursive clone contains every source dependency needed to build native releases.
  • The shipped renderer is first-party Go code and normal builds do not link virglrenderer, rutabaga, or another external renderer.
  • A standard Linux virtio-gpu/Mesa guest negotiates the supported VirGL capset without a custom guest kernel or Mesa fork.
  • Known scenes correctly exercise buffers, indexing, textures, sampling, blending, depth, scissor, resource copies, and vertex/fragment shaders.
  • Neurodesk reaches a usable accelerated desktop on an ARM64 Linux guest over HVF and runs the selected visualization corpus.
  • Native Glass consumes shared textures with explicit producer/consumer synchronization and no normal full-frame readback.
  • CPU snapshots continue to support 2D fallback, screenshots, and VNC/headless consumers.
  • Malformed protocol and shader inputs are bounded, fuzzed, and produce device/context failures rather than process panics.
  • Start, render, resize, detach/attach where supported, stop, and restart work repeatedly in the same daemon session.
  • macOS HVF passes the complete reference corpus; Linux KVM and Windows WHP pass it before acceleration is enabled by default on those hosts.
  • auto falls back cleanly while explicit virgl produces a structured failure when unavailable.
  • Renderer diagnostics expose negotiated capability, resource budgets, queue/fence progress, and context loss without depending on user-facing prose.
  • The renderer contract, resource ledger, and opaque native-frame handoff can add a Vulkan/Metal backend without exposing OpenGL identities through cc or the display API.
Success condition: a user launches NeurodeskAppX on Apple Silicon, works in an accelerated scientific desktop over time, resizes and restarts it safely, and gets the existing 2D desktop if acceleration cannot initialize. The same architecture then supports the Steam track rather than constraining it.
