SquadVM interface plan · August 2026

More useful pixels. More readable words.

Modernize the native SquadVM chrome around the guest without turning it into a new product. The setup and startup screens become compact control surfaces: clear at a glance, comfortable at normal viewing distance, and able to fit common laptop windows without clipping.

Scope: native viewer UI Targets: Windows · macOS · Linux No guest desktop redesign

Proposal in one sentence: replace the tall, poster-like composition with a persistent compact header, a two-column status grid, inline options, and one anchored action row—while making every meaningful sentence at least 14–16 logical pixels.

Design principles

What changes—and what does not

01

Text first

Primary copy is 16 px or larger. Secondary copy is 14 px or larger. Tiny uppercase text is reserved for short status tokens, never instructions or errors.

02

Density through structure

Recover space by using columns and removing ornamental gaps—not by shrinking controls, line height, or text.

03

One clear action area

Options live together; start/update actions live together. The eye should not travel across unrelated controls at the bottom edge.

04

Stable geometry

Checking, ready, update, and failure states share the same layout so content changes do not cause the whole interface to jump.

05

Logical pixels everywhere

Layout is calculated in logical units and rendered through the platform scale. A 16 px label should have the same perceived size at 100% and 200% DPI.

06

Guest remains primary

Once the desktop is ready, native chrome stays out of the way. Update notices remain compact, dismissible, and keyboard reachable.

Layout specification

A smaller footprint with larger type

The dimensions below are implementation targets, not fragile snapshot contracts. The layout engine should preserve relationships when available space changes.

Buttons50 px high44–48 px highRetains a generous target while tightening the footer.

Important: do not solve narrow windows by silently scaling the whole interface down. Reflow from two columns to one, wrap details where necessary, and allow vertical scrolling only below the supported minimum height.
Behavior and accessibility

Readable also means operable

✓

Keyboard navigation

Tab traverses options and actions in visual order; Space toggles the focused option; Enter activates the primary action; Escape returns to settings.

✓

Visible focus

Focused controls receive a high-contrast outline that is distinct from selected, enabled, and hover states.

✓

Errors get room

Error details may wrap to two lines or open a detail region. They must not be reduced to an unreadable ellipsis when remediation matters.

✓

Meaning beyond color

PASS, UPDATE, WAIT, and FAIL retain text or icons; progress includes a textual amount or activity description.

✓

Contrast budget

Normal text targets WCAG AA contrast. Muted text is brighter than the current tertiary purple-grey, especially at 13–14 px.

✓

No animation dependency

Indeterminate motion is supplementary. A static frame still communicates the current phase and operation.

Implementation sequence

Build it as a layout system, not another set of coordinates

Phase 1

Tokens and measurements

  • Centralize type sizes, colors, spacing, radii, and control heights.
  • Add text wrapping and measured truncation helpers.
  • Define supported logical viewport sizes.
Phase 2

Pure layout model

  • Return rectangles for header, status grid, options, and actions.
  • Share rectangles between drawing and hit testing.
  • Switch to one column at the compact breakpoint.
Phase 3

Render all states

  • Modernize preflight, ready, update, failure, and startup screens.
  • Align update notices with the same tokens.
  • Add focus and keyboard traversal state.
Phase 4

Platform review

  • Capture reference screenshots at supported DPI scales.
  • Check long errors and large byte/version values.
  • Have the Windows reporter retest the packaged build.
Verification

Acceptance criteria

✓

Fits common windows

The normal two-column setup view fits without clipping at 1024×640 logical pixels; compact mode remains usable at 760×520.

✓

Minimum readable sizes

No instructional or status-detail text below 14 logical pixels; no primary control label below 14 pixels.

✓

Objective layout tests

Tests verify non-overlap, bounds containment, minimum target sizes, correct responsive mode, and matching draw/hit rectangles—not exact prose or incidental coordinates.

✓

State coverage

Checking, first download, ready, image update, application update, combined updates, failure, cancellation, and desktop notification states are reviewed.

✓

DPI matrix

Windows 100/125/150/200%, macOS 1×/2×, and representative Linux scale values preserve logical geometry and crisp text.

✓

No workflow regression

First launch remains download-and-start; returning users still auto-start; Escape still reveals settings; the guest desktop keeps full ownership after readiness.

Non-goals

Keep this pass disciplined

This work does not redesign the guest desktop, introduce a general widget toolkit, change image/update policy, add onboarding pages, or replace the native OpenGL renderer. If the existing text renderer cannot support wrapping and focus affordances cleanly, add the smallest reusable primitives needed and stop there.
