Interaction plan

Behavioral contract

Pull flow

  1. Resolve the image tag to a digest and fetch the manifest.
  2. Check the content-addressed cache before requesting any layer.
  3. Download missing layers concurrently with resumable transfers.
  4. Report actual bytes, transfer rate, and ETA while totals are known.
  5. Verify every digest, then atomically commit the usable image.

A cached image skips straight to validation. An interrupted pull resumes verified partial content rather than starting over.

Start flow

  1. Prepare the writable image state, home, and shared storage.
  2. Start the VM and establish the guest control channel.
  3. Attach the graphics transport to an off-screen surface.
  4. Apply the current host window size and wait for desktop readiness.
  5. Present the first stable frame, then enable normal interaction.

The progress view owns the window until the final presentation gate passes. There is no interval where the framebuffer leaks through.

Progress semantics

  • Use determinate progress only when current and total are real measurements.
  • Switch to an indeterminate bar for validation, boot, and guest readiness instead of inventing a percentage.
  • Keep the primary label stable by phase; put changing detail in the secondary line so the UI does not visually jump.
  • Show layer-level detail on demand. Normal operation remains simple.
  • Cancellation stops new work safely; verified cached layers remain reusable. Failures keep a concise reason and offer retry.

Desktop readiness gate

All conditions must be true before the surface is presented:

  • The guest control channel reports the desktop session started.
  • The graphics connection has received a full framebuffer update.
  • The requested display size has been acknowledged and painted.
  • Keyboard, pointer, clipboard, and resize handlers are attached.
  • The frame has remained valid through one compositor paint cycle.

Readiness is a guest/display protocol event, not a timer and not a search for particular console text.

Event shape

The puller and VM session should emit structured events. Frontends choose wording without parsing logs. 

{
  "phase": "pulling",
  "message": "Downloading image",
  "current": 1702887424,
  "total": 2751463424,
  "unit": "bytes",
  "rate": 84934656,
  "eta_seconds": 12,
  "detail": "3 of 5 layers"
}

Terminal output remains available behind a diagnostic/debug option, but it is not used as the graphical startup surface.

Implementation slices

  1. Add typed pull and boot progress events to the backend API.
  2. Make the image cache resumable, verified, and atomic.
  3. Render the readiness view in the native graphics window.
  4. Add the guest and full-frame readiness handshake.
  5. Swap the hidden graphics surface into the window on readiness.
  6. Add recovery UI for offline, auth, disk-full, and guest failures.

Acceptance criteria

  • A first pull exposes real byte progress, rate, and ETA.
  • A cached start does not flash a redundant download phase.
  • An interrupted pull resumes without redownloading valid layers.
  • Cancel leaves the cache and image selection in a valid state.
  • No boot console or terminal content is visible by default.
  • No partial desktop frame is visible during startup or resize.
  • The first visible desktop accepts input immediately.
  • A startup failure stays in the progress view with retry details.
